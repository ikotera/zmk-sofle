## 1. 目的と基本方針

### 1.1 目的

分割キーボード（Eyelash Sofle / ZMK）の新しい配列に慣れるため、いまアクティブなレイヤーのキー配列と押下中のキーを、常に最前面の小窓に表示する。修飾付きのキーは「Shift+2」ではなく実際に入力される文字（`@`）で出す。あわせて、まれに起きる「キーリピートが止まらない」不具合の原因を突き止めるための記録を取る。

### 1.2 基本方針

| 方針 | 内容 |
|---|---|
| 個人用・自分の用途に特化 | 自分の Eyelash Sofle（USB の VID 0x1D50 / PID 0x615E）と macOS だけを対象にする |
| 省資源 | 常駐アプリなので、phys_footprint と無操作時の CPU を上限内に保つ（§11）。再描画は状態が変わったときだけ |
| 心地よさ | 入力中のアプリからフォーカスを奪わない（nonactivating な NSPanel）。シリアル通信は UI のスレッドの外で行う |
| 堅牢・安全 | キーマップの解釈と記録の判定はコア（LayerViewerCore）に置き、単体テストで固める。キーボードへは読み出しの要求しか送らない |
| 技術 | Swift（AppKit）＋ Swift のコア（§1.3） |

### 1.3 技術選定と理由

| 候補 | 判定 | 理由 |
|---|---|---|
| ブラウザ（WebHID・Web Serial・Document Picture-in-Picture） | 併存（`../layer-viewer/`） | 最初の版。動くが Chrome 本体のメモリが常駐する。記録機能は持たせない |
| Swift（AppKit）のみ、コアも Swift | 採用 | 約 20 MB で動く。HID・イベントタップ・シリアルは macOS の API を直接呼ぶのが最短。コアは数百行で、Rust にして FFI を挟む利点が小さい |
| Rust コア＋SwiftUI / GPUI | 不採用 | 規約の既定だが、この規模では FFI とビルドの手間がコアの利点を上回る。コアが大きくなったら再検討（§9 Q1） |

## 4. 仕様

### 4.1 表示

- 決定: キーマップと物理配列はキーボード本体から ZMK Studio RPC（USB シリアル）で読み、`~/Library/Application Support/LayerViewer/keymap.json` に保存する。レイヤーと押下中のキーはファームウェアの Raw HID レポートで受け取る。透過キーは下のレイヤーの割り当てを薄く出す。
- 決定理由: Studio で編集した内容（レイヤー名を含む）はリポジトリの `.keymap` に無い。
- 受け入れる欠点と対策: Studio でキーマップを変えたら手動で再取得が要る（メニュー）。

### 4.2 キーリピートの記録（S1）

- 決定: 3 か所の観測を突き合わせる。
  1. キーボード内部: Raw HID の押下中のキー位置（入力監視の許可は不要）
  2. Mac が受け取った HID: Sofle のキーボード用インターフェースの押下・解放（IOHIDManager。横取りしない）
  3. macOS のキーイベント: keyDown / keyUp とキーリピート（読むだけのイベントタップ）
  同じキーのリピートが 8 回続いたら「異常リピート」とし、その瞬間に 1 と 2 がそのキーをどう見ているかで判定する。

  | キーボード内部 | Mac の HID | 判定 |
  |---|---|---|
  | 押下中 | ― | キーボード内部で押下中（意図した長押し、または右手との通信などキーボード側の押しっぱなし） |
  | 解放 | 押下中 | 左手→Mac の送信で解放が失われた・遅れた |
  | 解放 | 解放 | macOS 以降の問題、または別のキーボードからの入力 |

  あわせて、文字キーが 1 秒以上押下中になったら（修飾キーを除く）、キーボード内部・Mac の HID のそれぞれで「長押し」を1行記録する。
- 記録先: `~/Library/Logs/LayerViewer/`。`events.log` に異常と印を1行ずつ、`incident-*.log` に直前 20 秒の観測を書き出す（「キーボード内部で押下中」以外の異常リピートと、利用者の印のとき）。
- 決定理由: 発生がまれで再現できないため、人の観察に頼らず、起きた瞬間の各層の状態を自動で残す。意図した長押し（Backspace の押し続け等）でもリピートは起きるので、それは1行だけにしてファイルを増やさない。
- 受け入れる欠点と対策:
  - キーボード側の押しっぱなしと意図した長押しは自動では区別できない → 起きたら 20 秒以内にメニューの「いま異常が起きた（印を付ける）」を押してもらう。
  - macOS のキーイベントは全キーボードから来る → 判定文に「別のキーボードの可能性」を含める。
  - 時刻はコールバックを受けた時刻（ミリ秒程度の誤差）。秒単位の現象を見るには十分。

## 5. 安全策

| 対象 | 対策 |
|---|---|
| キーボードへの書き込み | しない。Studio RPC は読み出しの要求だけ、Raw HID は購読の要求（先頭 0x4C）だけ |
| 入力の記録（プライバシー） | 記録するのはキーの番号と時刻だけで、文字列は組み立てない。ファイルに残るのは異常のときの直前 20 秒だけ。パスワード欄などの保護された入力（Secure Input）はイベントタップに届かない。メニューで記録を止められる |
| 権限 | 入力監視の許可が無いときは記録だけを止め、表示は続ける。許可されたら自動で記録を始める |
| 設定・記録の保存場所 | 設定は UserDefaults（`com.ikotera.layerviewer`）、キーマップは `~/Library/Application Support/LayerViewer/`、記録は `~/Library/Logs/LayerViewer/` |

### 8.5 S1 の詳細（v1.1.0）

- 記録の判定はコアの `Recorder` に置いた。時刻を外から渡すので、単体テストで時間を進めて判定を確かめられる（19 件）。

- 署名を Apple Development の証明書に変えた。署名が毎回同じになるので、入力監視の許可がビルドのたびに外れない（推測。許可を出し直さずに再インストールして記録が始まることは確認済み）。
- 画面: 小窓の右上に「● 記録中」と版。メニューに「記録」「いま異常が起きた（印を付ける）」「記録フォルダを開く」「入力監視の設定を開く」と版。
- 確かめたこと: 擬似の F19 リピート（CGEvent に autorepeat を付けて送る）で、判定「Mac の HID では解放済み」の incident ファイルが出た。
- 制限: 実機のキーボードを押したときの「Mac の HID」の記録は、利用者の打鍵が要るため未確認（§6）。

### 8.6 S2 の詳細（v1.1.1）

発端（2026-10-14 01:05、R-006）: 「3について」と打とうとして `u` が 9 回リピートした。記録と macOS のシステムログ（`/usr/bin/log show`）を突き合わせると次のとおり。

| 時刻（01:05） | 出来事 | 出典 |
|---|---|---|
| 09.339 | `u` を押す | 記録 |
| 09.823〜10.495 | WindowServer が `u` を約 83 ms ごとに 9 回リピート（ATOK にも届いている） | システムログ |
| 09.38〜10.54 | 記録アプリには何も届かない | 記録 |
| 10.543〜10.546 | `u` の解放、`i`・`h`・`,`・かな、キーボードの報告、リピートがまとめて記録アプリに届く | 記録・システムログ |

- 確かなこと: macOS は `u` の解放を約 1.2 秒受け取れず、その間リピートした。まとめて届いたキーは全部右手のキーだった。システム全体は止まっていない（WindowServer・ATOK は動き続けていた）。
- 記録の誤り: 記録アプリも同じ 1.2 秒イベントを受け取れず、受け取った時刻で判定したため「Mac の HID では解放済み」と誤判定した。
- 記録アプリが止まった原因（推測）: 2 秒ごとの購読の要求（`IOHIDDeviceSetReport`）は同期呼び出しで、キーボードが応答するまでメインスレッドを止める。キーボード（左手）が USB で約 1 秒応答しなかったなら説明がつく。そうであれば、右手のキーの遅れと合わせて、左手（central）が約 1.2 秒止まっていた可能性がある。右手との通信だけが止まった可能性も残る。
- 修正:
  - 観測の時刻をカーネルが受け取った時刻にした（Raw HID は `IOHIDDeviceRegisterInputReportWithTimeStampCallback`、HID は `IOHIDValueGetTimeStamp`、キーイベントは CGEvent の timestamp）。記録アプリに届いた時刻も別に持つ。
  - 判定は、記録した観測を発生した順に並べ直し、リピートの時点までに発生したものだけで行う。
  - 0.5 秒以上遅れて届いた観測があれば「配送の遅れ」として1行記録する。incident ファイルの各行には「届くまで」の秒数を付ける。
  - 購読の要求を、メインスレッドではなく専用のキューで送るようにした（前の要求の応答待ちなら重ねない）。最初は応答を待たない `IOHIDDeviceSetReportWithCallback` にしたが、このアプリでは以後の入力レポートが届かなくなった（同じ呼び出しを単体のプログラムで試すと届いた。原因は未解明）。
  - 調査用に、`LAYERVIEWER_DEBUG=1` で起動すると Raw HID の接続・要求・受信を標準エラー出力に出す。
- 次に発生したときに分かること: キーボードの報告と Mac の HID の「発生した時刻」で、`u` の解放がいつ Mac に届いたかが分かる。解放の発生時刻が遅ければキーボード側（右手との通信、または左手の停止）、早ければ macOS 側。

### 8.7 2026-10-14 23:52 の発生の分析（R-007。v1.1.1 の記録）

| 相対秒 | 出来事 |
|---|---|
| -9.591 | `e`（位置 16、左手）を押す。キーボード内部・Mac の HID・macOS が同時刻 |
| -9.088〜-8.502 | macOS が `e` を約 84 ms ごとに 8 回リピート |
| -8.501〜-8.497 | `u`（右手）の押下と解放、`.`（右手）の押下と解放、`e` の解放が約 4 ms の間にまとめて出る（キーボード内部の報告も同時） |

- 確かなこと: 記録アプリへの配送の遅れは無い（「届くまで」の注記が無い）。`e` の解放は、キーボード内部（左手）の時点で約 0.9 秒遅れていた。その間に打った右手のキーも、同じ瞬間にまとめて処理された。
- ソースで確かめたこと: 左手自身のキーの読み取り（`physical_layouts.c` の kscan メッセージ処理）と、右手から届いたキー（`split/bluetooth/central.c`）は、どちらもシステムワークキューで処理される。
- 推測: 左手（central）のシステムワークキューが約 0.9〜1.2 秒止まった。01:05 の発生も同じ形で説明できる。
- 止めた処理の候補（推測）: システムワークキューで行う設定の保存（フラッシュへの書き込み）。`CONFIG_ZMK_RGB_UNDERGLOW_AUTO_OFF_IDLE=y` では、30 秒の無操作と再開のたびに RGB の点灯・消灯処理が呼ばれ、RGB と外部電源の状態の保存が 60 秒後に予約される。ただし NVS は前回と同じ値なら書き込まない（`nvs_write` が比較する）ので、RGB を点けていなければ影響しない。
- 確かめ方の案: ファームウェアでシステムワークキューの遅れと `settings_save_one` の所要時間を測り、Raw HID で送って記録する。

### 8.8 S3 の詳細（v1.2.0、ファームウェアのレポート v3）

- 前提（R-008）: RGB はキーを押すと点灯し、30 秒の無操作で消える設定（`CONFIG_ZMK_RGB_UNDERGLOW_AUTO_OFF_IDLE=y`、RGB はオン）。この場合、無操作と再開のたびに RGB と外部電源の状態が実際に変わるので、60 秒後のフラッシュへの書き込みが本当に起きる（ソースで確認）。手を止めずに 60 秒以上打っていると、打鍵中に保存が走る。
- 計測（ファームウェア `src/layer_report.c`）:
  - システムワークキューの遅れ: 20 ms ごとのタイマーで計測用の仕事を投入し、実行までの時間を測る。前の仕事が残っていれば投入し直さないので、止まっていた時間がそのまま測れる。100 ms 以上なら変化を待たずに報告する。
  - 設定の保存: `settings_save_one` をリンカーの `--wrap` で受け、所要時間・回数・名前の先頭 3 文字を記録する。
  - レポート v3: 押下中のキーを 128 キー分（[8..23]）に縮め、[24..31] に計測値を入れる。表示アプリが聞いているときだけ計測する。
- 記録（Layer Viewer）: 遅れが 150 ms 以上なら「キーボードの停止」とし、前後 5 秒以内の設定の保存を添えて記録し、incident ファイルも書き出す。設定の保存は1行ずつ記録する。レポートの解釈はコア（`LayerReport`）に移して単体テストした。
- 対策（`config/eyelash_sofle.conf`）: `CONFIG_ZMK_SETTINGS_SAVE_DEBOUNCE=3600000`（1 時間）。無操作と再開のたびに保存が延びるので、保存はほぼ無操作中に走る。
- 次に分かること: リピートが起きたとき「キーボードの停止」が記録され、保存が重なっていれば仮説を支持する。対策後は打鍵中の保存がほぼ無くなるので、停止そのものが無くなれば対策が効いた、残れば別の原因（そのとき保存が重なっていないことも記録で分かる）。
- 推測のまま: 停止の原因がフラッシュの消去（NVS の空き領域の整理）か、書き込みそのものか。
